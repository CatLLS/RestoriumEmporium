### OPEN (informational / for the human, not blocking)

3. **Contract §6 safety-timeout wording vs. `TutorialController`'s actual behaviour** — SEVERITY: LOW. Contract: *"Every gated step keeps a safety autoAdvanceSeconds ... so nothing can soft-lock."* Every step authored by `TutorialAuthoringTool.cs` does carry a non-zero `autoAdvanceSeconds`. However, in `TutorialController.RunStep` the elapsed-time check that would actually use it is gated behind `useSafetyTimeout` (`while (!_advanced && (!useSafetyTimeout || elapsed < timeout))`), and `useSafetyTimeout` **defaults off** and every handoff/checklist explicitly says to leave it unticked in the real scene ("steps wait for the player… tick only to burn through the script while testing"). So in production, `autoAdvanceSeconds` is inert — soft-lock protection in practice comes entirely from every gated step having an always-achievable advance condition (which the anchor audit above confirms is true today), not from the timeout. This is a deliberate, well-reasoned, well-documented trade-off (see the component's own KEY DECISIONS comment), not a bug — flagging only because a literal reading of the contract sentence promises more than the shipped behaviour provides. No code change made; nothing to fix, just worth the human's awareness if a future step is authored with an anchor that can silently stop existing (e.g. an item renamed away from `lamp`).
4. **UI.md §7 "lamp price/id lock-in" concern is already satisfied** — checked directly: `ShopItemWizard.cs`'s `Starters` array has `new Starter("lamp", 100, ...)`, matching `deskhub_lamp`'s `requiredItemId: "lamp"` step exactly (both id and the "coins earned == lamp price" price of 100). ## Disputes — resolved

**(a) Does `catBoard` belong to `DeskHubScreen` (permanent room decor) or to the tutorial-only `HubTracyOverlay`?**
**Resolved: tutorial-only, belongs to `HubTracyOverlay`.** Verified by comparing the actual screenshots: `Docs/Batch2/screens/Desk_Hub.png` (the full-body-Tracy dialogue frame) shows the corkboard with pinned notes and the cat; `Docs/Batch2/screens/enteredEditMode.png` and `PreviewMode.png` (the two frames that represent actual `DeskHubScreen` states, no Tracy) show a plain wall/shelf with **no corkboard at all** in that spot. This means `catBoard.png` is not baked into the shared `zoomoutBG.png` room background and is only ever shown while the full-body Tracy overlay is up. `Assets/Scripts/Tutorial/TracyOverlayView.cs`'s own checklist (§ "SECOND INSTANCE — HubTracyOverlay") already documents this exact reasoning and places `CatBoard` as a `HubTracyOverlay` child, and `SHOP.md` independently flags the same conclusion. Both agents agree, the screenshots confirm it, overriding the lead's placeholder "permanent decor" assumption. **No code change needed** — already built correctly.

**(b) `RestorationController.beginOnStart` must be `false` in the scene.**
**Resolved: correct as designed, not a bug.** The field defaults to `true` in code (`RestorationController.cs:117`) *on purpose* — its own tooltip and checklist explain it exists so a single poster can be tested standalone without the rest of the flow wired up. Both CORE.md (§3) and RESTORATION.md (§3B) independently and consistently instruct the scene builder to untick it in the real `Game.unity`. This is a deliberate "safe default for isolated testing, explicit instruction for production" pattern, not a contradiction. Carried into the "Human menu run order" / scene-builder checklist below as a **must-verify** item since it's exactly the kind of single-checkbox trap that silently breaks the flow if missed (GameFlowController would race with RestorationController's own auto-start).

**(c) Does the handoff tell the builder exactly how `FinishedRepairScreen`'s reveal (via `CardFlipAnimator`) is wired through the `UnityEvent`?**
**Resolved: yes, fully, split across two files' checklists (by design — see KEY DECISIONS in `FinishedRepairScreen.cs`: the two halves are deliberately independent, connected only by a `UnityEvent`, never by a typed reference).** `Assets/Scripts/UI/FinishedRepairScreen.cs`'s checklist (§C) says exactly: *"On Shown (+): drag the FlipCard object in and pick CardFlipAnimator → Play() (add that component to FlipCard first)."* `Assets/Scripts/Restoration/CardFlipAnimator.cs`'s own checklist then gives the FlipCard-specific field wiring: *"Face Image ← FrontFace… Back Face Source ← only for the FinishedRepair card: drag BackFace in."* `CardFlipAnimator.Play()` is confirmed to exist, public, parameterless (compatible with a `UnityEvent`), and its own doc comment says explicitly: *"This is what FinishedRepair screen's On Shown uses."* Nothing missing. **No code change needed.**

**(d) `PauseButton` on `StickerRemoval`/`Cleaning`/`Linen` screens.**
**Resolved, with two fixes made (see "FIXED" above).** `StickerRemovalScreen.cs` (new screen) already had complete, correct instructions. `CleaningScreen.cs`/`LinenBackingScreen.cs` (pre-existing MVP files) did not — and `PauseButton.cs`'s own checklist incorrectly asserted the hamburger objects already existed in the scene, which is false (verified against `Game.unity` directly — see FIXED #1). Both gaps are now closed by direct edits to the three files' checklists. `DeskHubScreen`'s hamburger is intentionally different (wired directly to `OverlayController.OpenSettings()` per contract §5/§9's flow description, not a `PauseButton` component) — confirmed consistent between `DeskHubScreen.cs`'s code and both SHOP.md and PauseButton.cs's checklist. `FinishedRepairScreen` and `Journal`/`Shop` correctly have **no** hamburger (not "during restoration" / explicitly excluded by contract).
